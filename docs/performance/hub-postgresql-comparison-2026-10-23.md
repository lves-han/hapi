# HAPI PostgreSQL 与 SQLite 生产性能对比 2026 年 10 月 23 日

当前 PostgreSQL 部署的会话列表中位耗时为 **4.555 ms**，旧版 SQLite 基线为 **1,071.312 ms**；按相同的 5 轮本机请求测法，耗时降低 **99.57%**，旧/新耗时比为 **235.2×**。追加的 100 轮固定负载采样中，会话列表 p95 为 **6.208 ms**，200 次 HTTP 请求全部成功。

此前由会话列表同步聚合查询引起的单核瓶颈已修复。本轮每秒执行 5 次会话列表请求和 5 次健康检查，持续 20 秒，Hub 主线程平均 CPU 为 **2.95%**。两条热点查询已命中定时消息部分索引，预热后的中位耗时均约 **0.24 ms**。

资源变化同时记录：Hub RSS 从 **883.352 MiB** 降至 **467.148 MiB**；加入 PostgreSQL 后，Docker 内存显示值合计约 **1.74 GiB**，旧版为约 **0.87 GiB**。原始样本、计算结果和执行计划见 [对比 JSON](hub-postgresql-comparison-2026-10-23.json)，旧值来自 [SQLite 基线](hub-sqlite-baseline-2026-10-22.md)及其 [原始 JSON](hub-sqlite-baseline-2026-10-22.json)。

## 单核 99% 问题的根因与修复证据

旧故障记录中，主线程的 `ps %CPU` 生命周期平均值为 **99.1%–99.8%**，Docker 单次 CPU 样本为 **102.34%**。旧版会话列表会执行两条同步聚合 SQL，分别统计未来定时消息数量和最早发送时间；SQLite 选择 `idx_messages_local_id` 时，会扫描会话的历史消息。旧基线两条 SQL 的 wall 中位耗时合计约 **1,057 ms**，CPU 中位耗时也接近这一数值，与会话列表约 1,071 ms 的总耗时相符。

当前查询使用异步 PostgreSQL 存储并命中 `idx_messages_scheduled_pending`。在本轮零待发送消息的数据下，两条查询均实际扫描 **0 行**，各命中共享缓存 **2 块**，读取磁盘 **0 块**。其预热后 wall 中位耗时约 0.24 ms；每秒 5 次会话列表请求时，主线程平均 CPU 为 2.95%，健康检查 p95 为 1.094 ms。这些执行计划与负载样本确认了本次定位的同步聚合瓶颈已解决。

旧故障期 CPU 与当前负载窗口分别保留各自的时间与计算口径；相同 5 秒低流量测法的 CPU 对照见下节。

## 热点 SQL 与执行计划

两条查询均覆盖 `default` 命名空间全部会话，使用固定的毫秒时间参数，保留 `invoked_at IS NULL`、`local_id IS NOT NULL`、未来 `scheduled_at` 及 `delivery_state = 'queued'` 条件。

旧版使用内置 Bun/SQLite，在同一只读事务中测量 prepare、执行与 finalize。当前通过 Bun 原生 SQL、单连接池，在 PostgreSQL `REPEATABLE READ READ ONLY` 事务内测量客户端完整往返，并设置 15 秒语句超时。每条查询先保留 3 次样本，与旧基线并列；再执行 `EXPLAIN (ANALYZE, BUFFERS)`，预热 3 次并记录额外 50 次。

| 查询 | 旧原计划 3 次中位 ms | 当前 3 次中位 ms | 旧/新耗时比 | 当前额外 50 次中位 ms | 当前额外 50 次 p95 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 定时消息数量 `scheduled_count` | 530.186 | 1.554 | 341.2× | 0.2405 | 0.872 |
| 最早发送时间 `scheduled_min` | 526.592 | 0.899 | 585.8× | 0.2370 | 0.295 |

PostgreSQL 的 `EXPLAIN ANALYZE` 服务端执行时间分别为 **0.037 / 0.033 ms**，规划时间为 **0.547 / 0.525 ms**；上表 wall 时间包含 Bun SQL 客户端与连接往返。旧版 `cpu_ms` 与当前探针的 `client_cpu_ms` 在原始样本中分别标注。

旧版基线中，SQLite 指定同一定时消息索引的中位耗时已达到 **0.124 / 0.168 ms**。这一对照说明索引选择是本轮改善的重要来源；当前部署还包含异步调用链和 PostgreSQL 后端的变化。

## 采样完整性与复现信息

采样采用以下顺序，业务服务与客户端保持运行：

1. 记录容器、进程、配额、宿主机状态，执行 5 秒被动资源采样。
2. 在 PostgreSQL 只读事务中统计 12 张表，采集两条聚合 SQL 的原始时间与执行计划。
3. 执行 5 轮历史口径 HTTP 对照，再执行 100 轮固定负载采样。
4. 使用旧备份镜像只读复测 SQLite，最后汇总最近 180 秒的脱敏路由耗时。

最近 180 秒日志包含本次探测：会话列表完成 118 次，格式化平均 2.508 ms、最大 3 ms；健康检查完成 141 次，格式化平均 0.085 ms、最大 1 ms。日志时长为整数毫秒或整数秒，精细延迟采用 HTTP 原始样本。

已核对的完整性条件：

- 本轮 5 轮对照和 100 轮负载的全部 HTTP 请求返回 200。
- PostgreSQL 聚合逐次匹配独立候选记录计算结果，SQLite 原计划与指定索引结果一致。
- 采样期间 Hub 和 PostgreSQL 的 PID、镜像 ID 保持一致。
- 采样后保留的 SQLite 主文件和 WAL 的 SHA256 与部署切换记录一致。
- 仓库 JSON 通过凭据、JWT 与未脱敏会话 UUID 检查；业务正文和完整日志保留在本机受限环境。

本轮采样器保留于 `/data/dev/tmp/hapi-postgres-performance-20261023/collect.py`，复用了旧采样器的 `/proc`、HTTP 和日志统计方法；两份采样器摘要保存在 JSON。原始生产数据为零待发送定时消息，固定负载为每秒 5 轮；1、1,000 条待发送消息的生成数据结果见 [PostgreSQL 本地验证记录](postgresql-validation-2026-10-22.md)。后续复测沿用相同指标，使用新的输出文件保存各轮结果。
